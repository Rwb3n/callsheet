## 2. Event Bus

Contract: `shared-infrastructure.md` §1.2 (`EventBus` interface), §1.3 (sync/async classification), §1.4 (P1–P5), §1.5 (consumer health monitoring).

### 2.1 Module Layout

```
src/lib/event-bus/
├── bus.ts       ← InProcessEventBus class
├── types.ts     ← Re-exports from shared-infrastructure types
├── matrix.ts    ← EVENT_CONSUMER_MATRIX + validateConsumerRegistration()
├── errors.ts    ← logEventConsumerError() → DB
└── index.ts
```

### 2.2 Implementation Decision: `waitUntilFn` Injection

The bus receives `waitUntil` as a parameter to `emit()`, not as a constructor dependency. The caller (tRPC procedure or API route) passes the request-scoped `waitUntil` from Vercel's `next/server`. In tests, pass a no-op or `Promise.all` collector.

**Implementation extends SI contract [S0-7]:** SI §1.2 defines `emit(event: EventPayloadMap[T])` as the abstract contract. The implementation adds `eventType` (for handler lookup) and `waitUntilFn` (for Vercel lifecycle integration). These are implementation details — the contract surface (event types, payloads, handler registrations) is unchanged.

```typescript
async emit<T extends EventType>(
  eventType: T,
  payload: EventPayloadMap[T],
  waitUntilFn: (promise: Promise<void>) => void
): Promise<void>
```

Dispatch order: sync handlers sequential + awaited → async handlers via `waitUntilFn`. Sync failure propagates + logs. Async failure logs only. [Source: SI §1.2]

### 2.3 Startup Validation

`validateConsumerRegistration()` iterates `EVENT_CONSUMER_MATRIX`, checks that for every entry a handler with matching `domain` + `mode` is registered. Missing handler = startup failure. Multi-mode per domain supported (e.g., PP has both sync and async consumers for `claim_approved`). [Source: SI §1.5]

### 2.4 Scaling Metric

Log per event-emitting request: `syncDurationMs`, `asyncConsumerCount`, `asyncPercentage` (of total request duration). Threshold: >30% sustained 7 days → evaluate migration. [Source: SI §1.7]

## 3. Deferred Action Scheduler

Contract: `shared-infrastructure.md` §2 (types, registered actions, execution model).

### 3.1 Module Layout

```
src/lib/scheduler/
├── registry.ts  ← registerActionHandler(), typed handler map
├── poll.ts      ← pollDeferredActions(), executeAction()
├── api.ts       ← scheduleDeferredAction(), cancelDeferredAction()
└── index.ts
```

### 3.2 Implementation Decisions

**Polling interval:** 60 seconds, configurable via `SCHEDULER_POLL_INTERVAL_MS`.

**Retry backoff:** Exponential — `Math.pow(2, attempt) * 60 * 1000` → 120s, 240s, 480s. Previous formula (`Math.pow(5, attempt) * 12`) produced a 25-minute gap at attempt 3 — too aggressive for transient failures. [S0-4]

**Sequential execution:** No parallelism within a poll cycle at V1. Add `pg_advisory_lock` if scaling to multiple workers.

**Recurring actions [S0-6]:** Actions like `billing_reconciliation` and `notification_cleanup` are "24h recurring." Pattern: the action handler schedules its own successor as its final step — `scheduleDeferredAction({ action: same, executeAt: now + 24h })`. Application startup seeds the first instance if no pending action of that type exists (`SELECT 1 FROM deferred_actions WHERE action = $1 AND status = 'pending'`). This is self-perpetuating — no cron, no separate mechanism.

**S0 registers two shared handlers:** `auto_escalation_check` (§4), `notification_cleanup` (90-day bulk delete, batch `LIMIT 10000` per execution [S0-16]). Feature slices register domain handlers during module init.

### 3.3 Public API

```typescript
async function scheduleDeferredAction<T extends keyof DeferredActionParamsMap>(params: {
  action: T
  params: DeferredActionParamsMap[T]
  executeAt: Date
  retryPolicy: "once" | "retry_3"
  onFailure: "log" | "alert_principal"
  createdBy: string
}): Promise<UUID>

async function cancelDeferredAction<T extends keyof DeferredActionParamsMap>(params: {  // [S0-5]
  action: T
  filterParams: Partial<DeferredActionParamsMap[T]>
  cancelledBy: string
}): Promise<number>  // count cancelled
```

## 4. Orchestrated Flow Engine

Contract: `shared-infrastructure.md` §3 (types, generic orchestrator, auto-escalation, skip constraints).

### 4.1 Module Layout

```
src/lib/orchestrator/
├── engine.ts      ← executeOrchestratedFlow(), resumeOrchestratedFlow(), skipFlowStep()
├── escalation.ts  ← handleAutoEscalationCheck() deferred action handler
└── index.ts
```

### 4.2 Implementation Decisions

**Context persistence:** The shared `TContext` object is serialised to JSONB in `orchestrated_flows.context` after each step completes. On resume, deserialised and passed to the next step.

**Auto-escalation scheduling:** `executeOrchestratedFlow()` schedules `auto_escalation_check` deferred actions at flow creation. Erasure flows: daily checks when ≤7 days to deadline, weekly otherwise. Closure flows: weekly only (no statutory deadline). Handler re-schedules itself if flow is still active. [Source: SI §3.4]

**Escalation handler logic:**
1. If `flow.status === "completed"` → no-op.
2. Erasure deadline: ≤0 days → CRITICAL alert + escalate. ≤3 days → auto-escalate. ≤7 days → notification.
3. Retry exhaustion: `currentStep.attempt >= 3` → auto-escalate.
4. Re-schedule next check if flow still active.

**Skip enforcement:** `skipFlowStep()` checks `step.skippable` before allowing skip. Non-skippable steps throw. Skip constraint matrix defined in SI §3.5.

## 5. Auth (Better Auth)

Contract: `shared-infrastructure.md` §4 (session type, role model, NFRs).

```typescript
// src/lib/auth.ts — Better Auth config
export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg" }),
  emailAndPassword: { enabled: true },
  emailVerification: {
    sendVerificationEmail: async ({ user, url }) => {
      await emailService.send({
        to: user.email, template: "email_verification",

```

**tRPC middleware chain:** `publicProcedure` (no auth) → `protectedProcedure` (auth required) → `adminProcedure` (admin role required). Admin check uses `role.startsWith("admin")` for V2 scoped-role compatibility. [Source: SI §4.1]

**Custom field [S0-8]:** Better Auth supports `additionalFields` in its config to extend the `user` table. S0 uses this to add `role: text("role").default("user")` to the Better Auth-managed user table. This avoids a separate CALLSHEET accounts table for role storage. `accountId` throughout CALLSHEET = Better Auth `user.id`. S1 adds CALLSHEET-specific tables (Account profile, Listing, etc.) referencing `user.id` as the foreign key. The role field lives on the auth-managed user table, not on S1's Account table — auth middleware reads it directly without a join.

## 12. tRPC Setup

```typescript
// src/server/trpc.ts
export const router = t.router
export const publicProcedure = t.procedure
export const protectedProcedure = t.procedure.use(authMiddleware)
export const adminProcedure = t.procedure.use(authMiddleware).use(adminMiddleware)

// src/server/root.ts — slices add sub-routers incrementally
```

### 12.1 Error Handling [S0-13]

**Standard error shape:** tRPC `errorFormatter` produces a consistent structure for all procedures:

```typescript
type FormattedError = {
  code: TRPCErrorCode          // UNAUTHORIZED, FORBIDDEN, BAD_REQUEST, INTERNAL_SERVER_ERROR, NOT_FOUND
  message: string              // human-readable
  fieldErrors?: Record<string, string[]>  // Zod validation errors, keyed by field name
}
```

**Auth error mapping:** 401 → `UNAUTHORIZED` (no session). 403 → `FORBIDDEN` (session present, insufficient role). These are set by `authMiddleware` and `adminMiddleware` respectively.

**Server-side logging:** All `INTERNAL_SERVER_ERROR` responses are logged as structured `console.error` with stack trace, tRPC path, and input (sanitised — no passwords/tokens). `BAD_REQUEST` (validation failures) are not logged — they are expected client errors.

### 12.2 Service Injection [S0-18]

Services are injected via tRPC context. `createContext()` resolves `Services` based on `process.env.NODE_ENV`:

```typescript
// src/server/context.ts
export async function createContext() {
  const services = process.env.NODE_ENV === "test"
    ? createTestServices()
    : createProductionServices()
  return { services, session: await getSession() }
}
```

All procedures access services via `ctx.services`. No direct imports of production service implementations in procedure code.

## 13. Open Question Resolutions

### PP-Q2: Testing Strategy

Three tiers: Vitest (unit + integration), Playwright (E2E).

| Tier | Tool | Scope | Run When |
|---|---|---|---|
| Unit | Vitest | Pure functions, type transforms, computation | Every commit (pre-commit hook) |
| Integration | Vitest + test DB | Event consumers, deferred actions, tRPC + DB | CI on every push |
| E2E | Playwright | Critical user paths: signup, claim, subscribe, search | CI on PR, nightly |

Vitest over Jest for ESM compatibility with Next.js App Router. Test DB: Supabase local (Docker), fresh schema per suite via Drizzle migrations.

### PP-Q3: Error Monitoring

Structured logging to stdout + Vercel Log Drain. No external service at V1.

| Concern | V1 Approach | Migration Trigger |
|---|---|---|
| Error capture | `event_consumer_errors` table + structured `console.error` | >10 uncaught/day → Sentry |
| Request tracing | Vercel trace ID | Cross-consumer debugging needed → OpenTelemetry |
| Alerting | Admin dashboard on next login + auto-escalation (§4.2) | Missed critical errors → PagerDuty |

### PP-Q4: CI/CD Pipeline

GitHub Actions: `lint-and-type` → `test-unit` → `test-integration` (parallel). `test-e2e` on PRs only. Deploy via Vercel on main branch push (after CI passes). Preview deployments for PRs.
