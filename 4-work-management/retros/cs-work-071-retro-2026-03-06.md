# Retro: CS-WORK-071 — Revenue perception and metrics

**Date:** 2026-03-06
**Scope:** CS-WORK-071 (8 AC). 8-metric RevenuePerception computation, evaluateRevenueHealth thresholds, commercial.getRevenuePerception adminProcedure route.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `createTestListing` fixture requires `(db, accountId, overrides)` — not a single options object. The impl plan wrote `createTestListing({ accountId: OWNER, name: "..." })` which failed on type check. The `replace_all` fix then broke syntax by removing the opening brace. Lesson: always verify fixture signatures during pre-check, not during test writing. |
| **What went well?** | Domain logic was straightforward — spec pseudocode mapped almost 1:1 to implementation. The `evaluateRevenueHealth` pure function needed zero iteration. All 23 tests passed on first run after the fixture fix. `PRICING` const from CS-WORK-066 and `churn_analysis_log` schema were exactly right for the aggregate queries. |
| **Could have gone better?** | Integration tests for `computeRevenuePerception` use small dataset sizes (5 paid, 5 churned) rather than the spec's example values (95 current paid, 5 churns → 5%). The test still validates the formula correctly, but the numbers are less intuitive at a glance. |
| **Keep doing** | 3-agent parallel pre-read (spec + code + test patterns). The IO profile `db-read` correctly predicted no schema changes needed — just aggregate queries against existing tables. |
| **Stop doing** | Using `replace_all: true` for broad string replacements that might partially match surrounding syntax. The `createTestListing({ accountId:` → `createTestListing(db, OWNER` replacement broke the opening brace of the overrides object. |
| **Start doing** | Verify test fixture function signatures during `/impl` Step 3 pre-check, not first encounter in test code. Add `createTestListing(db, accountId, overrides?)` to the mental model before writing tests. |
