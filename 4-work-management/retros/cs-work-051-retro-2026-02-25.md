# Retro: CS-WORK-051

**Date:** 2026-02-25
**Scope:** CS-WORK-051 — Implement listing profile page and contact feedback (12 AC, S6 §2 + §7)

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The targeted claim CTA (AC-14) interacts with the contact fallback branch in a non-obvious way. The spec describes the targeted claim as upgrading the generic claim CTA, but the generic claim CTA only appears when there's zero contact info — yet the targeted claim needs the website URL for domain comparison. This created a precedence issue: targeted claim must be checked *before* the contact fallback branch fires, otherwise listings with a matching website domain would show "Contact Provider" instead of the targeted claim. Required restructuring `resolveProfileCTA` to evaluate the targeted claim first and only fall through to contact if it doesn't match. |
| **What went well?** | Pure function extraction was clean and testable. `inferSource`, `resolveProfileCTA`, and `generateJsonLd` are isolated, zero-dependency functions with full test coverage. The existing event type infrastructure (`EventPayloadMap`, `_brand` pattern, `EVENT_CONSUMER_MATRIX`) absorbed the payload updates without breaking any of the 550 existing integration tests — only 3 test files needed `timestamp` field additions. The profile page decomposition into `page.tsx` / `data.ts` / `emit.ts` keeps concerns separated and avoids pulling the event bus into static builds. |
| **Could have gone better?** | `emitProfileViewed` had to be stubbed because the production event bus is not accessible from server components. The bus is created and injected at `createAppRouter()` bootstrap, but server components don't have access to that singleton. This means AC-18 (profile_viewed emission) is structurally correct and tested via integration tests, but the actual runtime emission won't fire until the tRPC API route handler is wired. This is a known gap from the deferred `onTRPCError` wiring. Also, the `CompaniesHouseService` stub in the test had to return `{ found: false }` not `null` — a recurring friction point with that interface type. |
| **Keep doing** | Reading existing integration test patterns before writing new ones. The `createUnclaimedListing` helper with overrides, the `emptyConsumerMatrix` pattern, and the `createWaitUntilCollector` pattern all worked first try. Type-checking before running tests catches structural issues faster. Running the full integration suite after type changes confirms no cascade breakage. |
| **Stop doing** | Writing test assertions that match TRPCError code strings (e.g., `toThrow("NOT_FOUND")`) — the message property contains the human-readable message, not the code. This caused 5 of 8 initial test failures. Use `.toThrow()` (bare) or match on the actual message text. |
| **Start doing** | Standardise a `toThrowTRPCError(code)` custom matcher or helper that checks `error.code` instead of relying on string matching against `error.message`. Would eliminate the recurring NOT_FOUND / "Listing not found" mismatch. |

## 2 — Classification

| # | Item | Bucket | Detail |
|---|------|--------|--------|
| 1 | Targeted claim CTA precedence over contact fallback | Bug | Spec ambiguity caused the initial implementation to check contact fallback before targeted claim. The CTA decision tree needed restructuring: targeted claim must be evaluated before the contact branch. Fixed during implementation. |
| 2 | Pure function extraction pattern (inferSource, resolveProfileCTA, generateJsonLd) | Feature | Clean separation of concerns. Functions are testable in isolation. Pattern works well for buyer-facing page logic. |
| 3 | Event type updates absorbed without cascade breakage | Feature | Adding `timestamp` and narrowing union types on `ProfileViewedEvent` and `ContactAttemptEvent` only required 3 test file updates. Consumer handlers that don't use the new fields were unaffected. |
| 4 | `emitProfileViewed` stubbed — no production event bus in server components | Feature request | The event bus is wired at app bootstrap via `createAppRouter(services)`. Server components (page.tsx) can't access it. Need a production bus singleton or alternative emission mechanism for server component contexts. |
| 5 | TRPCError assertion mismatch (`toThrow("NOT_FOUND")` fails) | Refactor | `.toThrow(string)` matches against `error.message`, not `error.code`. Every listing router test that asserts NOT_FOUND has this friction. Need a standardised assertion pattern. |
| 6 | `CompaniesHouseService` stub must return `{ found: false }` not `null` | Refactor | The interface type requires a non-null return. Every test file that stubs this service repeats the same `{ found: false }` boilerplate. Could be a shared fixture. |
| 7 | Profile page `data.ts` uses direct DB queries (not tRPC) | Feature | Server components access the DB directly via `getDb()`. This is correct for SSG — no tRPC layer needed. The pattern should be reused for any future SSG pages. |
| 8 | AC-44 rate limit partially implemented | Upgrade | The rate limit is enforced at the Zod/route level (input validation + event emission). Full per-IP/per-user rate limiting requires persistence (Redis or DB) which is out of scope for V1. The AC is covered by the guard conditions (unclaimed-only, no-email-only) which limit abuse surface. |
