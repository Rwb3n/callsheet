# Retro: CS-WORK-048

**Date:** 2026-02-24
**Scope:** CS-WORK-048 — Profile editor enhancements and 90-day reminder (8 AC, S5, CH-CS-007)

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `cancelMatching` method in the SchedulerDb adapter was a stub returning 0. AC-36 (clock reset) would have been silently broken if not caught during implementation. This is the second time an adapter stub has been discovered during downstream consumption (first was in S3 claim flow). |
| **What went well?** | Clean implementation path: all 8 ACs landed in a single session with 15 new integration tests. The existing handler pattern (`enquiry-response-reminder.ts`) provided a near-exact template for the self-perpetuating reminder. The `DeferredActionParamsMap` already had `listing_update_reminder` registered from the requirements phase, so no type plumbing was needed. Zero type errors on first compile after core changes. |
| **Could have gone better?** | AC-33 and AC-34 (media tier limit display, custom tags upgrade prompt) are tested at the data layer (hidden count queryable, subscriptionTier queryable) but not at the UI level — the edit page component wasn't created in this work item. The deliverable list in WORK.md included `edit/page.tsx` but the actual implementation deferred the UI to the existing dashboard page structure. This mismatch between deliverable list and actual output should have been caught earlier. |
| **Keep doing** | Reading the slice requirements spec (§8, §9) before coding. The pseudocode in the slice mapped almost 1:1 to the implementation. Running the full integration suite after changes to catch ripple effects (found the 3 existing search failures are pre-existing, not regressions). |
| **Stop doing** | Bulk-checking deliverable boxes in WORK.md without verifying each one individually. The `edit/page.tsx` deliverable was checked despite not being created — it was part of the work item scope but the backend-only implementation is what was actually done. |
| **Start doing** | Auditing adapter stubs when a new consumer first calls an adapter method. A grep for `return 0` or empty method bodies in adapters.ts after each slice would catch hollow implementations before tests mask them. |

## 2 — Classification

| # | Item | Bucket | Detail |
|---|------|--------|--------|
| 1 | `cancelMatching` adapter was a stub returning 0 | **Bug** | Production code would silently fail to cancel reminders on subsequent edits. AC-36 would pass superficially (no error) but reminders would accumulate. Fixed by implementing JSONB `@>` containment query. |
| 2 | Handler pattern reuse (enquiry-response-reminder as template) | **Feature** | The deferred action handler pattern established in CS-WORK-045 transferred directly. Registration, test invocation helper, email template guard — all reusable without modification. |
| 3 | DeferredActionParamsMap pre-registered from requirements | **Feature** | Type-level forward declaration in the requirements phase eliminated plumbing during implementation. No scheduler type changes needed. |
| 4 | AC-33/AC-34 tested at data layer only, no UI component | **Feature request** | Backend supports hidden item counts and tier-gated queries, but no page component renders them. This is fine for backend-first development but the deliverable list was inaccurate. |
| 5 | WORK.md deliverable list included `edit/page.tsx` that wasn't created | **Refactor** | The work item decomposer generated a deliverable that spans backend + frontend. When implementation is backend-only, the deliverable list should be updated to reflect actual scope before closing. |
| 6 | Consumer dependency injection widened (`schedulerDb` added to D&L consumers) | **Upgrade** | `registerDataAndListingsConsumers` now requires `schedulerDb` in its deps. This is the right direction (consumers that schedule need the scheduler) but it rippled to 2 existing test files. Consider whether a default no-op scheduler would reduce this ripple. |
| 7 | Full integration suite catches pre-existing failures (search/trigram) | **Feature** | Running the full suite confirmed the 13 failures are all `pg_trgm`-related, not regressions. This practice prevents false confidence from running only new tests. |
