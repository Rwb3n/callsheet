# Retro: CH-CS-014 W5–W8 — Shell, search page, profile styling, dashboard pages

**Date:** 2026-02-25
**Scope:** W5 (application shell, 4 AC), W6 (search page, 6 AC), W7 (profile styling, 4 AC), W8 (dashboard pages, 4 AC). 18 AC total, 10 files created, 4 files modified.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | React Query v5 replaced `keepPreviousData` with `placeholderData: (prev) => prev`. The tRPC v11 types caught this at compile time. Also: nested `<main>` landmarks — the root layout initially used `<main>`, but 4 existing pages already had their own `<main>`. Changed to `<div>` immediately. |
| **What went well?** | All 4 work items completed in a single pass. W5→W6/W7/W8 dependency chain resolved cleanly. The existing tRPC router types provided compile-time verification of all data shapes — no runtime surprises. shadcn primitives (Badge, Card, Button, Skeleton, Input) covered all UI needs without additional components. 0 type errors, 944 tests passing throughout. |
| **Could have gone better?** | The search page client component is ~250 lines — approaching the limit where extraction would help readability. The `ListingCard` and `FacetGroup` sub-components are internal. If these are needed elsewhere (profile page, shortlists), they should move to `src/components/`. |
| **Keep doing** | Reading router types before building pages. The exported `ListingSummary`, `SearchResultOutput`, and `ListingCardData` types eliminated all guesswork. |
| **Stop doing** | Using deprecated React Query APIs from memory. Always check current version. |
| **Start doing** | For pages consuming tRPC data, start with the type exported from the router, not with a visual design. The type dictates what's available. |
