# Retro: CH-CS-014 W1 — Production services factory + event bus singleton

**Date:** 2026-02-25
**Scope:** W1 of CH-CS-014 (Presentation Layer). First work item of the horizontal chapter. 4 AC, 7 new tests, 3 files created, 2 files modified.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The event bus singleton inherently needs a live database (via `getDb()` → `createLogEventConsumerError`), making what was spec'd as a "unit" test (AC-02) actually an integration test. The singleton pattern couples init to the full DB adapter chain. |
| **What went well?** | Clean mapping from `AppServices` type to existing adapter factories — every field already had a `create*Db()` adapter in `src/db/adapters.ts`. Zero new abstractions needed. The existing `auth-instance.ts` singleton pattern transferred directly. All 4 AC verified in one pass. No rework. 945 tests, 0 failures, 0 type errors. |
| **Could have gone better?** | AC-04 (`onTRPCError` wiring) is half-verified — the function export and shape are tested, but the actual wiring into `fetchRequestHandler({ onError })` happens in W2. The AC sits in W1 but its proof-of-completion is in W2's route handler. Could have been assigned to W2. |
| **Keep doing** | Reading all dependency files before writing code. The full read of bus.ts, adapters.ts, all consumer barrels, and the waitUntil module meant zero discovery surprises during implementation. |
| **Stop doing** | Initially writing the singleton test as a unit test then having to rename it. Should have checked the dependency chain (singleton → `getDb()` → `DATABASE_URL`) before choosing the test file suffix. |
| **Start doing** | For production singletons that touch DB, default to `*.integration.test.ts` upfront. Add a mental checklist: "does this call `getDb()` anywhere in the init chain?" |
