## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | Adding `"cross-domain"` to the `decisionDomainEnum` pgEnum required a `drizzle-kit push` to the running Supabase instance. The TypeScript type change compiled fine but the DB rejected the insert at runtime. The `/impl` Step 3 type alignment check identified the enum mismatch but didn't flag the DB push requirement — the integration tests caught it. |
| **What went well?** | Clean separation of concerns: `evaluate.ts` (pure evaluation logic), `dispatch.ts` (orchestration + logging), `graduation.ts` (admin routes). Unit tests used a thenable mock DB pattern that handles Drizzle's variable-length chains. Integration tests covered the full dispatch → log → bounds → override cycle. 7/7 AC in a single implementation pass after the enum push fix. |
| **Could have gone better?** | Unit test mock DB failed on first attempt — the chainable mock didn't handle Drizzle's implicit promise resolution at arbitrary chain positions. Required a second attempt with a thenable chain pattern. The governance bounds ordering (log before vs after bounds check) caused the 11th-dispatch test to fail — the spec's pseudocode shows log-then-check, but the correct semantics are check-then-log so the current evaluation doesn't count against its own bound. |
| **Keep doing** | Running `drizzle-kit push` immediately after pgEnum changes, before integration tests. The error message ("invalid input value for enum") is clear but costs a test cycle. |
| **Stop doing** | N/A |
| **Start doing** | When adding a pgEnum value, include a `drizzle-kit push` step in the implementation plan as an explicit prerequisite before integration tests. |
| **Skill amendment?** | `/impl` Step 3 item 5 (enum value pre-read) covers reading enum values but doesn't flag that *adding* an enum value requires a DB push. Add: "If the work item adds a new pgEnum value, include `drizzle-kit push` as Step 0 of the implementation order (before any integration tests)." |
