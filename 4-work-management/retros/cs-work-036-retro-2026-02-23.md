## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | How trivially small the implementation was. 4 source files, ~80 lines of production code total, 200 lines of tests. The spec's §4.2 showed `enforceFeatureGate(listingId, feature)` doing a DB lookup, but the AC table said "Unit" test type. The WORK.md said "no DB dependencies." Resolving this contradiction (accept `tier` not `listingId`) took more thought than writing the code. |
| **What went well?** | TIER_LIMITS already existed from CS-WORK-010 (S1 media upload). `computeFeatureAccess` is a trivial spread on top of it. The three gating value types (`false`, `"none"`, `0`) were explicit in the spec — no ambiguity about what "gated" means. Clean first-time test pass. |
| **Could have gone better?** | The spec/WORK.md interface mismatch (`listingId` vs `tier` param) could have been caught during decomposition. The decomposer writes AC from the spec verbatim, but the WORK.md context says "no DB." A quick consistency check during decomposition would prevent this class of contradiction. |
| **Keep doing** | Grouping pure-function work items together. No DB, no event bus, no scheduler — just types and tests. Fast execution, clean isolation. |
| **Stop doing** | Nothing specific — this was frictionless. |
| **Start doing** | Consider whether `enforceFeatureGate` should also accept a `listingId` overload that does the DB read, so S5/S6 don't each have to write the "read listing, pass tier" boilerplate. Not urgent — rule of three applies. |
