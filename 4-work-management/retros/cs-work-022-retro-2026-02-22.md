# Retro: CS-WORK-022 — Article 14 GDPR Compliance

**Date:** 2026-02-22
**Scope:** CS-WORK-022 implementation session. 2 AC, 3 deliverables (source file, test file, migration). Schema change + DeferredActionParamsMap extension + template registration.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | Module-level `registerTemplate()` side effects don't re-execute on dynamic `import()` in Vitest because the module is already cached. First test run failed on all 4 email-sending tests. Fix: extract registration into a named function with `hasTemplate()` guard, export it, call explicitly in `beforeEach` after `clearTemplates()`. The module-level call still runs for production. This is the first time template registration and test lifecycle collided — previous templates were registered in modules that tests didn't `clearTemplates()` around. |
| **What went well?** | 1. S0 infrastructure composed cleanly — `EmailService`, `DecisionLogDb`, `SchedulerDb` all injected via constructor params, no monkey-patching. 2. The spec (S2 §6.5, §11, §12) was precise enough that implementation was mechanical — every function boundary, template field, and deferred action param was pre-specified. 3. Work item was small-effort as estimated: 2 AC, one source file, one test file, one migration. Start-to-green in a single pass after the template registration fix. 4. All 228 tests pass (130 unit + 98 integration) with 0 type errors. No regressions in the existing 222-test suite. |
| **Could have gone better?** | 1. The test file has two inline DB adapter factories (`createDecisionLogDb`, `createSchedulerDb`) that duplicate the Drizzle-to-interface wiring from other test files. These will recur in every test that uses the scheduler or decision log. Rule of three hasn't triggered yet (this is the second instance after CS-WORK-021's integration tests) but will on S2 onboarding. 2. The `article_14_progress_check` handler itself is not implemented — only the scheduling of the deferred action. The handler that checks send progress and alerts the principal will arrive with S2 AC-42/AC-44. This is spec-correct (those ACs are in S2's Article 14 Compliance group, not CS-WORK-022) but worth noting. |
| **Keep doing** | Dependency injection for all infrastructure (email, scheduler, decision log, DB). Every test creates its own adapter instances — no shared mutable state between tests. The `InMemoryEmailService` + `clearTemplates()` + explicit registration pattern is reliable once understood. |
| **Stop doing** | Using module-level side effects for template registration without considering test lifecycle. The `clearTemplates()` in `beforeEach` wipes the registry, and ESM module caching means the module-level `registerTemplate()` won't re-run on subsequent imports. |
| **Start doing** | Consider a shared test helper for `createSchedulerDb(db)` and `createDecisionLogDb(db)` — these are pure Drizzle-to-interface adapters that will be needed in every integration test touching S0 infrastructure. Extract on the third usage (likely S2 onboarding). |
