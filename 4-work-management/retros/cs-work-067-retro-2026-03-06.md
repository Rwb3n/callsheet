## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The spec prescribes file paths under `src/server/commercial/` but the established codebase convention is `src/domains/commercial/`. Caught early from decomposition lesson ("check spec file tree first") — no wasted work. Also, `bus.emit()` takes 3 args (eventType, payload, waitUntilFn) not 2 — discovered only at type-check time, not from reading the spec pseudocode which omits the waitUntilFn parameter. |
| **What went well?** | Single-pass implementation: all 13 AC verified on first test run. No test failures to debug. The pre-check of existing code (engagement router, taxonomy overlap, listing-helpers, email templates) before writing any code paid off — every import path was correct on first attempt except the `accountProfiles.email` miss. Total wall-clock: ~15 minutes from spec reading to green suite. |
| **Could have gone better?** | The `accountProfiles` table has no `email` column — email lives on the Better Auth `user` table. This is a recurring pattern (3rd time hitting it). The `getEngagementCounters` function was re-implemented inline instead of importing from the engagement router — the router exports the type but not the standalone query function. Two copies of the same logic now exist. |
| **Keep doing** | Reading all source files in parallel before writing any code. Using `evaluateConversionTrigger` wrapper for integration tests instead of only testing via the tRPC route — this gives direct access to `TriggerResult` and `TriggerAction` for merge field assertions. |
| **Stop doing** | Assuming `accountProfiles` has an email field. Always use `user.email` from `@/db/schema/auth` for account email lookups. |
| **Start doing** | Extract `getEngagementCounters(db, listingId)` as a standalone exported function (not just a tRPC route handler) so domain modules can import it without duplicating the query. |
