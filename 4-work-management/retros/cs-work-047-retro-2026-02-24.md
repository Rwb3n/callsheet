## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The S5 spec (§7.2) references `listing.paddleCustomerId` but the actual schema stores it on `accountProfiles.paddleCustomerId`. The S4 subscription router already handles this correctly — the spec pseudocode diverges from implemented reality. This is the kind of spec drift that could cause a bug if implemented literally. |
| **What went well?** | S4 infrastructure made this trivially small. `getSubscriptionStatus` already returned tier, cadence, dates, feature access, and grace period. `PaymentService.getCustomerPortalUrl` was already defined in the interface and mocked. Only net-new code was `getPortalUrl` (~20 lines) + the page placeholder. 10 integration tests, all passing first run. |
| **Could have gone better?** | The WORK.md deliverables listed extending the dashboard router, but the correct location was the subscription router (domain co-location). The deliverable description was misleading — led to a micro-decision during implementation that shouldn't have been necessary. |
| **Keep doing** | Placing new procedures on the domain-owning router (subscription router) rather than the consuming router (dashboard). Keeps the ownership model clean and avoids cross-domain leakage. |
| **Stop doing** | Nothing specific for this work item — clean execution. |
| **Start doing** | When decomposing work items, verify which router already owns the relevant procedures before specifying "extend router X". The decomposer assumed dashboard; implementation correctly chose subscription. |
