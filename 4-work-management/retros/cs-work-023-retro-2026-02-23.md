# Retro: CS-WORK-023

**Date:** 2026-02-23
**Scope:** CS-WORK-023 — Article 14 compliance handlers (3 AC, S2 onboarding slice)

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `correspondence_log` FK constraint on `listingId` caught a dummy UUID in the "day 30+ no reschedule" test. Using a fake `listingId` for correspondence entries is not viable — FK enforces referential integrity even in test data. Every test helper that inserts into `correspondence_log` must reference a real listing row. |
| **What went well?** | Clean decomposition: pure `computeArticle14Progress()` function handles all math (testable without DB), handler wires DB queries + side effects. Existing patterns (handler registration, `createSchedulerDb`, `createDecisionLogDb`, `createUnclaimedListing`) composed without modification — CS-WORK-018's handler pattern translated directly. 17 tests, 3 AC, first pass minus one FK fix. |
| **Could have gone better?** | Test initially used a dummy listing ID (`00000000-...`) for correspondence log insertion to avoid creating a full listing row — caught by FK constraint. This is the same class of error as CS-WORK-022's `decision_logs.accountId` UUID issue: test fixtures that bypass FK relationships will fail against a real DB. |
| **Keep doing** | Extracting pure computation into separate exported functions (`computeArticle14Progress`) rather than inlining in the handler. Makes unit-style assertions possible within integration test files without needing separate unit test files for small modules. |
| **Stop doing** | Using placeholder IDs for FK columns in test data. Always use a real parent row or pass the FK column as `null` (if nullable). |
| **Start doing** | Nothing new — existing patterns held. |
