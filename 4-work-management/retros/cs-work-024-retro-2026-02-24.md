# Retro: CS-WORK-024 — 4rfv SQLite extraction + cleaning

**Date:** 2026-02-24
**Scope:** CS-WORK-024 (4rfv extraction). 8 AC, high effort, infrastructure arc. Profiling → taxonomy mapping → extraction → pipeline integration.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `companies` table was a stripped merge output missing the most valuable fields (`description`, `contact_person`, `products_services`). The raw `companies_all` table was the real source. Also, `company_subcategory.company_id` references `companies_all.id`, not `companies.company_id` — using the wrong FK silently produced plausible but wrong subcategory assignments for every row. Without the `verify-join.ts` diagnostic script, this would have shipped undetected. |
| **What went well?** | Profile-first approach. Writing the profiling script before any extraction code meant every cleaning function had concrete evidence behind it. The taxonomy mapping hit 100% coverage on first pass (target was 90%) because the category-level fallback and keyword rules covered the long tail. Integration test caught nothing because the extraction was already type-safe — which is the right outcome. |
| **Could have gone better?** | The initial profiling script used wrong column names (`postcode` instead of `postal_code`, `email` instead of `primary_email`) in the "Specific Quality Checks" section, producing misleading zero-match results. Caught and fixed, but wasted a cycle. The column names were visible in the schema printout immediately above — should have cross-referenced before running. |
| **Keep doing** | Profile before extract. Write throwaway diagnostic scripts (`check-subcat-join.ts`, `verify-join.ts`) to validate assumptions about FK relationships before building on them. Run coverage checks (`check-coverage.ts`) as fast feedback loops before committing to a mapping strategy. |
| **Stop doing** | Assuming FK relationships from column names. `company_subcategory.company_id` looked like it referenced `companies.company_id` but didn't. Always verify joins empirically on unfamiliar schemas. |
| **Start doing** | Add a "FK verification" step to the profiling script for any multi-table extraction. Auto-detect which table a FK column actually references by checking value overlap against all candidate tables. |

## 2 — Classification

| # | Item | Bucket | Detail |
|---|------|--------|--------|
| 1 | Profile-first workflow: profiling report drives extraction logic | Feature | Produced a 867-line `data-profile.md` with extraction decision log. Every cleaning function has a traceable rationale. |
| 2 | Taxonomy mapping achieved 100% coverage via 3-tier fallback (override → keyword → category) | Feature | 790 subcategories → 269 CALLSHEET specialisations. The long tail of niche subcategories (78 with ≤2 companies) is handled by category fallback. |
| 3 | Diagnostic scripts as validation tools | Feature | `check-subcat-join.ts` and `verify-join.ts` caught the FK mismatch before it reached production code. Low cost, high value. |
| 4 | Wrong column names in initial profiling script | Bug | Used `postcode`/`email`/`website` instead of `postal_code`/`primary_email`/`primary_website`. Produced zero-match quality checks. Fixed on second run. |
| 5 | FK assumption: `company_subcategory.company_id` → `companies.company_id` | Bug | Silent data corruption. Every company would have received wrong subcategories. Caught by empirical verification script. |
| 6 | No automated FK verification in profiling | Feature request | The profiling script should auto-detect FK targets by checking value-set overlap across tables. Would have caught issue #5 without a separate diagnostic script. |
| 7 | Entity type inference limited to name heuristic | Upgrade | CH number is 100% null. Name pattern (Ltd/Limited) catches 23.8% as companies. The remaining 76.2% are classified as freelancers, but some are companies without "Ltd" in the name. A future enrichment pass (Companies House API lookup by name) could reclassify. |
| 8 | Region derived from city via hardcoded lookup table | Upgrade | Covers major UK cities but misses smaller towns. A postcode-to-region lookup (using outcode → region mapping) would give better coverage. Not worth building now — city coverage is 92.6%. |
| 9 | Taxonomy mapping is a static override table | Refactor | 200+ lines of manual overrides in `taxonomy-map.ts`. Works but is brittle — adding new CALLSHEET specialisations requires manually extending the map. A fuzzy matching approach (Levenshtein distance or TF-IDF on subcategory names) would be more maintainable at scale. Not justified for a one-time import. |
| 10 | Some companies get wrong services from category fallback | Upgrade | "020 Locksmiths Ltd" gets `entertainment-law, production-accounting, production-insurance` from the "Support Services" category. The company is in 4rfv's data but doesn't fit the broadcast/film domain. Pipeline Phase 1 may flag these via quality heuristics, but no explicit out-of-domain filtering exists. |
