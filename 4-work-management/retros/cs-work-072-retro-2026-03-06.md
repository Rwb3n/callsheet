# Retro: CS-WORK-072 — Feature gate friction, low-quality intervention, and refund evaluation

**Date:** 2026-03-06
**Scope:** CS-WORK-072 (13 AC). Three decision architectures: feature gate friction evaluation, low-quality intervention pipeline (notification + deferred action), refund evaluation.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `NotificationDb`, `SchedulerDb`, and `DecisionLogDb` interfaces use different method names than expected. Initial code used `.create()`, `.schedule()`, `.log()` which don't exist — the actual API is `createNotification(db, params)`, `scheduleDeferredAction(db, params)`, `logDecision(db, params)` wrapping `.insert()`. The wrapper functions are the public API, not the interface methods directly. |
| **What went well?** | Three independent decision architectures (friction, refund, quality) implemented in a single work item with zero test failures after the API fix. All 26 tests passed on first run. The `FeatureGateFrictionSummary` type from CS-WORK-064 (Ops) was a perfect fit — no adapter needed. The `bus.on()` pattern for event capture in tests was already established in winback tests. |
| **Could have gone better?** | The `ConsumerEntry` type does not accept a `handler` field — attempted to pass handler inline via consumer matrix in the test. Had to switch to `bus.on()` pattern. Should have checked the winback test pattern first. |
| **Keep doing** | Grouping related pure functions into a single work item. Friction + refund were both pure decision functions — zero DB interaction. Kept the test files clean and fast (unit tests ran in 4ms). |
| **Stop doing** | Guessing interface method names. Always read the interface definition (or grep for existing usage) before writing the first call. |
| **Start doing** | Nothing new — the pattern of reading sibling handler implementations (win-back) before writing new handlers proved effective once applied. |
