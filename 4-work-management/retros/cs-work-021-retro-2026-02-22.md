# Retro: CS-WORK-021 — 4rfv Import Pipeline

**Date:** 2026-02-22
**Scope:** CS-WORK-021 implementation session. 7 AC, 11 deliverables, migration + 8 source files + 4 test files.

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | UK postcode OCR fix was harder than expected. The naive "replace O→0 and l→1 globally" approach broke valid postcodes like `OX1 1AB` where `O` is a real letter. Required structural parsing — split outward/inward, apply OCR fixes only in digit-expected positions. Three iterations to get right. |
| **What went well?** | Spec-to-code fidelity was high. The S2 §6.1–§6.8 sections mapped directly to file boundaries and function signatures. AC-26 and AC-47 verified by architectural guarantee (no bus/email dependency in function signature) plus integration assertions. Two-phase listing creation pattern from S1 transferred cleanly. Total: 44 tests (37 unit + 7 integration), zero regressions against the existing 175-test suite (final: 130 unit + 92 integration = 222 total). |
| **Could have gone better?** | 1. The `db.execute()` return type for raw SQL queries in Drizzle ORM is awkward — `QueryResult<Record<string, unknown>>` requires `as unknown as` cast to access `.rows`. The integrity module's `nameSimilarity()` hit this. A thin wrapper would reduce friction for any future raw SQL. 2. Phase 3 (export flagged) is a `console.log(JSON.stringify(...))` stub — acceptable per spec ("stub for S7") but won't survive any real usage. 3. Integration test for the "filters dissolved" scenario initially had a wrong assertion (`dissolved === 0` instead of `1`) because the test comment was misleading about which records reach phase 2. |
| **Keep doing** | Running the full test suite (unit + integration) after every work item. The 222-test run catches regressions immediately. Typecheck before tests catches structural issues even faster. |
| **Stop doing** | Writing test assertions based on prose comments ("dissolved only applies to records that pass phase 1") rather than tracing the data flow. The comment was correct but the assertion was wrong — should have traced the actual record flow: 3 records → phase 1 flags 1 → 2 reach phase 2 → 1 dissolved. |
| **Start doing** | Consider a `rawQuery<T>()` helper that wraps `db.execute()` and returns typed `T[]` instead of requiring the `as unknown as { rows: T[] }` pattern. Would clean up the integrity module and any future pg_trgm usage. |
