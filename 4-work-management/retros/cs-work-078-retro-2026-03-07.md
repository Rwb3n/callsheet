# Retro: CS-WORK-078

**Date:** 2026-03-07
**Scope:** CS-WORK-078 — Analytics pipeline and feature gating (18 AC, S9 §3)

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The `perception_aggregates.listingId` FK constraint blocked the spec's "global sentinel aggregate row" for zero-result terms. The spec described a sentinel UUID approach but the schema has `NOT NULL` + FK to `listings`. The fix was straightforward (query `zero_result_queries` directly) but required post-merge surgery on Agent A's output. Spec-schema mismatches like this should be caught during `/impl` type alignment analysis, not during agent output review. |
| **What went well?** | 3-agent parallel delegation worked cleanly. Main context did event type change + shared types first, agents produced independent files with no merge conflicts. Total wall time ~7 minutes for agent work vs estimated ~25 minutes sequential. All 65 new tests passed on first integration — no type mismatches between agents. The "main context as orchestrator" pattern from CS-WORK-077 validated again. |
| **Could have gone better?** | Agent C committed to `master` instead of its worktree branch (the worktree was checked out to the right branch but git committed to the shared working directory). Files ended up in the right place but the commit was on master, not the worktree branch. This is a worktree isolation gap — agents should verify `git branch` before committing. Agent B's worktree copy of `feature-access.test.ts` caused 4 spurious test failures until worktrees were cleaned up — vitest discovered both copies. |
| **Keep doing** | Pre-creating shared `types.ts` with all JSONB shapes + helpers before dispatching agents. Agents consumed it without modification — zero type drift. The spec constants block in agent prompts prevented cadence/threshold mismatches (lesson from CS-WORK-077 applied). |
| **Stop doing** | Leaving worktrees alive after merging agent output. The duplicate test file discovery (vitest running both main + worktree copies) caused confusing failures. Clean up worktrees immediately after cherry-picking files. |
| **Start doing** | In `/impl` type alignment check (Step 3), verify FK constraints on tables the work item writes to. The sentinel UUID approach would have failed at runtime — catching FK incompatibility during planning saves a round-trip. |
| **Skill amendment?** | `/impl` Step 3 item 2 (Type alignment check): add "FK constraint audit — for each table the work item inserts into, verify all FK columns accept the planned values (sentinel UUIDs, null listingIds, etc.)." |
