# Retro: CS-WORK-044

**Date:** 2026-02-24
**Scope:** CS-WORK-044 — Analytics display and quality score panel (S5, 10 AC)

---

## 1 — Reflection

| Prompt | Notes |
|--------|-------|
| **What surprised you?** | The spec's `mapAnalyticsToUI` signature passed `SubscriptionTier` as the first arg, but the actual gating logic depends entirely on `FeatureAccess` fields — the tier was redundant. Dropped it from the pure function signature, routing through `featureAccess` alone. Cleaner than the spec, same behaviour. Also: all S9 placeholder fields (search terms, demographics, benchmarking) are `null` with no intermediate stub — the type system captures this naturally via `T | null`. |
| **What went well?** | Clean separation of pure functions (`map-analytics.ts`) from router I/O. 19 unit tests cover every tier + period combination with zero I/O setup. Integration tests reuse the existing `createTestListing` + `InMemoryNotificationDb` fixtures without any new helpers. The `getListingDashboard` query consolidates listing, engagement, quality, feature access, and decay warning into a single round-trip join + 2 follow-up reads. No N+1. |
| **Could have gone better?** | The `getListingDashboard` handler is the longest procedure in the router (~80 lines including the select, mapping, explanation fetch, and decay check). Still under the 30-line function body rule when measured as pure procedure logic, but structurally it bundles 3 concerns (analytics, quality, decay). A future refactor could extract `fetchListingDashboard(db, listingId, accountId)` as a named function. Also: the `as SubscriptionTier` cast on line 199 of `dashboard.ts` persists — same pattern flagged in CS-WORK-043 retro #4 but not yet extracted into a narrowing helper. |
| **Keep doing** | Pure function extraction for tier-gating logic. The `mapAnalyticsToUI` tests run in <10ms total and cover all 4 tiers without touching the database. This pattern should extend to every feature-gate-dependent mapping in the codebase. |
| **Stop doing** | Nothing new to stop. |
| **Start doing** | Consider extracting a `loadListingForOwner(db, listingId, accountId)` shared query — `getListingContext`, `getListingDashboard`, and `getQualityExplanation` all perform the same ownership-check-then-404 pattern with slightly different select columns. A generic version could return the full row and let callers destructure. |
